# 01 架构设计

## 1. 目标

| 现状（`resource/`） | 新框架（`src/`） |
| --- | --- |
| 每类传感器自定义 SHM 环形缓冲（magic GIGE/IMU0/LIDA/PLC），读写双方约定结构体 | 统一走 Eclipse Zenoh pub/sub，统一 64B 帧头 + key 命名 |
| 只能本机读；跨机需另写转发 | 本机 peer 之间 SHM 零拷贝；跨机由 zenohd 路由器自动转发 |
| 新增传感器（如 PLC）需改读写双方代码 | 新增 = 新写一个 pub（SensorNode），消费者按 key 订阅即可 |
| 无统一监控 | 每个实例自动发布 status/meta/ctrl，Web 控制台统一查看与控制 |

## 2. 拓扑

```
            ┌───────────── 交换机 C (10GbE) ─────────────┐
   6×GigE 相机   2×速腾雷达    IMU(串口/网口)   PLC(UDP)
            │                                            │
  ┌─────────┴──────── 服务器 A ──────────┐   ┌──────── 服务器 D ─────────┐
  │ zenohd (router, :7447, REST :8000)   │◄──┤ zenohd (router) connect A │
  │   ▲ 127.0.0.1                        │   │   ▲                       │
  │ pub-camera-gige ─┐  peer↔peer SHM    │   │ AI/录制等 sub（peer）      │
  │ pub-lidar-rs  ───┼─► sub(AI, 录制…)  │   │                            │
  │ pub-imu / plc ───┘                   │   └────────────────────────────┘
  │ sync-master  netprobe  console:18100 │
  └──────────────────────────────────────┘
```

* **每台服务器一个 zenohd**（docker 或 systemd 原生，见 `broker/`）。
* 本机所有程序以 **peer 模式** 运行，`connect=tcp/127.0.0.1:7447`，`listen=tcp/127.0.0.1:0`。
  路由器通过 gossip 告诉各 peer 彼此的 127.0.0.1 locator，peer 之间直接建链 —— 这是 **SHM 零拷贝的前提**。
* 服务器 D 的 zenohd 连接 A，D 上的消费者订阅的数据由 A→D 路由器链路以普通 TCP 传输（一份流量，D 上多个订阅者共享）。
* 每个传感器只被一个 pub 进程打开（独占），其它程序全部通过总线获取。

## 3. 组件

| 目录 | 说明 |
| --- | --- |
| `common/python/sensorhub` | Python SDK：key、帧头、`SensorNode`、`GridTimer`、订阅工具、配置解析 |
| `common/cpp/sensorhub` | C++ 帧头（与 Python 字节级一致），供 C++ pub/sub（雷达等）使用 |
| `configs/sensors.yaml` | 唯一的传感器配置（由控制台编辑、版本化） |
| `broker/` | zenohd 配置与两种部署方式 |
| `console/` | Web 控制台（FastAPI + 原生 JS） |
| `pub_server/*` | 采集程序（每个一个目录、一个 Dockerfile） |
| `sub_client/*` | 消费程序 |
| `deploy/` | compose 模板与分文件部署 |
| `tasks/`（仓库根） | 拆分给其他人实现的任务 |

## 4. 数据面 / 控制面

* **数据面**：`{prefix}/{kind}/{name}/{channel}`，payload = 原始数据（可 SHM），attachment = 64B 帧头。
* **控制面**（全部由 `SensorNode` 自动提供）：
  * `.../status` 1Hz JSON：状态、各通道频率/带宽/延迟/同步误差/丢帧、设备信息（链路速率等）、当前参数
  * `.../meta` queryable：静态描述（别名、frame_id、分辨率……）
  * `.../ctrl` queryable：`describe` / `get_params` / `set_params` / 自定义 op
  * `.../event`：状态变化、错误、参数生效
  * liveliness `{prefix}/alive/{kind}/{name}`：在线判定（进程崩溃时路由器自动撤销）
* **配置**：控制台在 `{prefix}/cfg/sensors` 提供 queryable，保存/回滚后发布 `{prefix}/cfg/changed`；
  pub 可选择热加载（`ConfigWatcher`）或由运维重启。

## 5. 为什么这样设计

1. **帧头放 attachment**：payload 保持纯数据，SHM 缓冲可直接交给订阅者；控制台测频率/延迟只读 attachment，不碰 payload。
2. **统一时间网格**（见 05）：所有传感器的 `trigger_ns` 都落在 `k × period` 上，消费者按 `trigger_ns` 精确对齐，
   不依赖"到达顺序"；不同容器、不同进程无需互相通信即可同相位。
3. **自描述参数**（`ParamSpec`）：控制台无需为每种传感器写页面，参数表单自动生成；新增传感器零前端改动。
4. **拥塞策略 drop**：大数据通道慢订阅者只会丢帧，绝不反压采集线程（采集侧丢帧会破坏同步）。
